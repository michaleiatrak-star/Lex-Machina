## Implemented

G34H5 adds explicit, authenticated migration of the known legacy plaintext upload layout into the encrypted LME1 case store.

The migration:
- requires authenticated case `MANAGE` access;
- unwraps the current case data key only inside `withCaseDataKey`;
- preserves the original opaque `uploadId`;
- validates legacy manifest shape, filename, size and SHA-256 before migration;
- encrypts into the current secure upload store;
- decrypts the secure copy and re-verifies size/SHA-256 before removing the plaintext legacy upload;
- is idempotent and safe to resume after an interrupted migration when the secure copy already exists;
- removes empty legacy `incoming/`, `documents/`, `artifacts/` and `audit/` directories after successful migration;
- records a security event for completed or blocked migration.

## Fail-closed behavior

Unknown/non-empty legacy `documents/`, `artifacts/` or `audit/` content is not deleted or guessed.

Instead, migration returns a blocked report and preserves the unknown data.

Unexpected entries under legacy `incoming/` are also blockers.

This intentionally avoids silently deleting historical data whose storage semantics are not known.

## HTTP boundary

Production route:

`POST /api/cases/:caseId/migrate-legacy-storage`

The route is registered before the core app catch-all and requires:
- valid session;
- case `MANAGE` authorization;
- current case key version.

No browser-provided filesystem path is accepted.

## Security qualification

G34H5 does **not** claim secure erase of deleted plaintext blocks on SSD/flash media.

It guarantees application-level migration, verification-before-removal and fail-closed handling of unknown legacy data.
