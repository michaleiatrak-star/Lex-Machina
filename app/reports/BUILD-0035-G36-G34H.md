## G34H — encrypted case storage

G34H1-H4 provide CDK-backed authenticated encrypted storage for:
- original uploads;

- persisted document source/protected state;
- sensitive generated artifacts.

Case CDK rotation rekeys the encrypted stores together with the encrypted privacy vault.

### G34H5 — legacy plaintext migration

Legacy migration is explicit and case-scoped. It is not silently executed at application startup.

Endpoint:

`POST /api/cases/:caseId/migrate-legacy-storage`

Security properties:
- authenticated local session required;
- case `MANAGE` capability required;
- CDK exists only inside the trusted `withCaseDataKey` callback;
- known legacy uploads are hash/size validated before migration;
- encrypted copy is decrypted and re-verified before legacy plaintext is removed;
- same `uploadId` is preserved;
- migration is idempotent/resumable after a crash if the secure copy already exists;
- unknown/nonempty legacy `documents/`, `artifacts/`, `audit/` or unexpected `incoming/` entries block migration and are not deleted;
- migration completion/blocking is recorded in security events without clear case data;
- route is mounted before the core Express catch-all and covered by an authenticated HTTP test.

Important limit:
- filesystem removal is **not** claimed to be secure erase on SSD/flash storage;
- a legacy upload migrated through the current secure-store API receives the migration time as secure `storedAt`; the historical legacy `storedAt` is not yet carried into the secure manifest. This is a provenance/lifecycle refinement, not an encryption failure.
