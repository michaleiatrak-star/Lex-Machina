## 1. Persistent reversible vault

The reversible PII map no longer needs to exist only in process memory for production case-backed finalization.

Per-case storage:

```text
cases/<caseId>/
  private/
    privacy/
      vault.lmv
      vault-meta.json
```

`vault.lmv` is the authenticated encrypted source of reversible token mappings.

`vault-meta.json` contains non-secret operational integrity metadata only.

---

## 2. LMV1 envelope

Binary envelope:
- magic `LMV1`;
- schema version;
- cipher-suite id;
- case key version;
- vault generation;
- nonce length;
- AAD length;
- ciphertext length;
- nonce;
- AAD;
- ciphertext;
- AES-GCM tag.

Cipher:
- AES-256-GCM.

Privacy Vault Key:

```text
PVK = HKDF-SHA256(
  CDK,
  salt = caseId,
  info = "lex/privacy-vault/v1"
)
```

The CDK itself is not persisted in the vault directory.

AAD binds:
- schema version;
- caseId;
- vault generation;
- keyVersion.

## 3. Canonical payload

Decrypted payload is per case and document:

```ts
{
  schemaVersion: 1,
  caseId,
  generation,
  documents: {
    [documentId]: {
      counters,
      tokens: [
        { token, kind, value, createdAt }
      ]
    }
  }
}
```

The duplicate in-memory reverse key map is reconstructed after decrypt and is not serialized.

`PseudonymizationVault` now supports:
- validated hydration;
- canonical snapshot;
- `hasToken`;
- exact `resolveToken`;
- fail-closed unknown token resolution.

No public HTTP endpoint exposes the clear mapping.

## 4. Atomic writes

Vault mutation path:
1. authenticate/authorize case operation;
2. unwrap CDK only in trusted callback;
3. derive PVK;
4. read/decrypt existing vault;
5. mutate canonical mapping;
6. increment generation;
7. encode LMV1 with fresh nonce;
8. write `vault.lmv.partial`;
9. fsync and close;
10. re-read/decrypt/verify partial;
11. atomically replace `vault.lmv`;
12. write/fsync `vault-meta.json.partial`;
13. atomically replace metadata.

Per-case operations are serialized in-process to avoid lost updates.

The per-case queue cleanup was tested/fixed so completed serialization chains are released.

## 5. Runtime document integration

Production `LocalPrivateDocumentService` can now use the encrypted vault store.

The trusted document record persists in memory:
- media type;
- source extraction;
- caseId;
- protected chunks;
- in-memory hydrated vault view.

It does **not** retain a CDK.

Production HTTP behavior:
- review binds document to caseId;
- finalize resolves the authenticated case;
- case WRITE is required;
- current case keyVersion is read;
- CDK is unwrapped only inside `withCaseDataKey`;
- document vault is decrypted/updated/re-encrypted inside that callback;
- browser never receives CDK/PVK or token-to-clear mapping.

## 8. G34D rotation compatibility

Case CDK rotation now includes the encrypted privacy vault.

Before ACL/key cutover:
- old CDK decrypts current vault;
- vault is re-encrypted under the fresh CDK/new keyVersion;
- remaining user envelopes are prepared;
- case metadata and ACL key version are committed.

If the key cutover fails before commit, the vault is rekeyed back to the previous CDK.

After the case key commit is complete, a later audit-write failure no longer rekeys the vault back and cannot create a CDK/vault mismatch.

Validated revoke path:
- create mapping;
- grant second user;
- revoke user;
- CDK rotates;
- owner opens same mapping under keyVersion 2;
- revoked user has no ACL.
