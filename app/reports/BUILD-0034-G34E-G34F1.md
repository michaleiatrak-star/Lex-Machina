## 1. G34E — recovery/password lifecycle

Implemented:
- 256-bit random recovery code `LMR1_<base64url>`;
- code itself is never stored;
- HKDF-SHA256 derives recovery KEK from the code;
- second AES-256-GCM UMK envelope stored in `auth.sqlite`;
- recovery code generation requires current password confirmation;
- password confirmation uses the same Argon2id verifier/backoff as login;
- changing password rewraps the same UMK;
- authEpoch increments on password change;
- previous sessions are revoked;
- successful password change returns a fresh session;
- recovery decrypts the same UMK;
- recovery sets a new password;
- recovery rotates the recovery code automatically;
- old recovery code becomes invalid;
- authEpoch increments on recovery;
- previous sessions are revoked;
- existing case CDKs remain unchanged.

Validated property:
- SHA-256 digest of a real case CDK is identical before password change, after password change and after recovery.

Therefore password/recovery operations do not require case re-encryption.

## 3. G34F1 — transaction reauthorization foundation

Implemented an in-memory deanonymization authorization state machine.

Intent binds:
- sessionId;
- userId;
- caseId;
- artifactId;
- format DOCX/ODT;
- tokenized SHA-256;
- vault generation;
- case key version;
- purpose `DEANONYMIZE_AND_EXPORT`;
- five-minute expiry.

Authorization:
- case ACL requires REIDENTIFY;
- fresh password is verified through Argon2id;
- successful password confirmation resets trusted session full-authentication time;
- exact artifact state is re-resolved before grant issue;
- 90-second grant is bound to the same exact target.

Consumption:
- exact same user/session required;
- ACL REIDENTIFY checked again;
- artifact state/hash/vault generation/key version checked again;
- grant is marked consumed **before** caller may unlock the vault;
- second use fails;
- expired grant fails;
- target mutation fails;
- session lock/logout/expiry/authEpoch revocation automatically revokes pending grants/intents.

## 4. Why full G34F is still open

There is not yet a real DOCX/ODT tokenized artifact/deanonymization path.

Therefore G34F1 validates the authorization protocol foundation, but full G34F cannot be claimed until:
- G31D/G31E create real tokenized artifacts;
- the artifact resolver reads their exact persisted state;
- the deanonymization function requires a consumed G34F grant;
- no alternative clear-PII path bypasses that manager;
- sensitive-download tickets are implemented.
